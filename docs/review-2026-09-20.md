## Original structural proposals

### 1. Give explanation runs an explicit lifecycle

**Finding.** [SaulRoot](../src/surface/SaulRoot.tsx) owns capture listeners, snapshot/context caching, ports, revision guards, status, pinning and bookmarks. [The background handler](../entrypoints/background.ts) separately owns cancellation, prompting, streaming and saving. In particular, cancellation during the awaited save does not cancel the database transaction, and the handler posts DONE after that await without rechecking the signal.

**Reasoning.** The code already has useful revision guards, but ownership of late events and the save boundary spans two independently managed lifecycles. Further reading actions will add more opportunities for stale state unless those transitions become explicit.

**Recommendation.** First specify generation-versus-save cancellation semantics. Then extract a small `useExplanationRun` controller and a background run executor, with states for generating, saving, saved, stopped and failed. Keep DOM capture and card presentation outside that controller. Add deterministic cases for disconnect during save, new selection during a pending action, and late completion after retry. No state-machine package is necessary initially.

**Tradeoff.** More named modules and transition code, in exchange for fewer scattered guards and easier lifecycle tests.

**Caveat.** The close-during-save concern is from code inspection, not a reproduced data-loss bug. Once a persistent transaction commits, closing the card cannot reliably undo it. Preserve current automatic-history and bookmark semantics during extraction.

**Open questions.** Should closing during Saving allow the run to finish and persist? Should an interrupted generation ever be recoverable from history? Should card state survive a service-worker restart?

### 2. Make cross-context request and response contracts explicit

**Finding.** [The storage client](../src/storage/client.ts) permits caller-selected `sendDbMessage<T = any>` reply types, [tab arguments](../src/native/tabs.ts) use `Record<string, any>`, and [the tab view](../src/app/Tabs.tsx) stores its preview as `any`. DB payload duplication is fixed here, but replies and UI/native operation results still lack one shared contract. Native calls already have runtime validation in [protocol.mjs](../native/protocol.mjs).

**Reasoning.** Type assertions can conceal a mismatch between request, worker reply and UI expectations. Chrome runtime boundaries also need runtime validation; TypeScript alone cannot validate incoming messages.

**Recommendation.** Add request-keyed reply types and discriminated operation results, then use them in the clients and UI. Define allowed senders for each route and validate messages once at those boundaries. Retain the native protocol as the CLI/MCP authority; extend or derive from it rather than adding a competing schema.

**Tradeoff.** More explicit types and validators, but fewer unchecked casts and better failures at the source of a malformed request.

**Caveat.** This review did not establish an external-message exploit. Preserve the intentional content-script explanation/bookmark routes, the shared tab queue, dry-run defaults and current CLI/MCP compatibility.

**Open questions.** Should protocol types be generated from the existing native schemas or maintained with contract tests? Are content scripts intended to access every DB operation, or only the reading operations they use?

### 3. Version storage migrations and measure history-query scaling

**Finding.** [Startup](../src/storage/db.ts) runs a combined [schema/legacy-index cleanup script](../src/storage/schema.ts) and scans for missing readable-search rows on every database initialization. The latest-run lookup orders `llm_run` by creation time and rowid for each selection, without a supporting selection/time index. Using the repository schema in an in-memory SQLite diagnostic produced `SCAN llm_run` and `USE TEMP B-TREE FOR ORDER BY`. A candidate `(selection_id, created_at DESC)` index changed this to a covering-index search, while still sorting the rowid tie-breaker.

**Reasoning.** Versioned migrations make upgrade intent and interrupted-upgrade recovery testable. The query plan gives a concrete reason to investigate history growth rather than splitting the database class solely because of its size.

**Recommendation.** Before the next schema change, introduce ordered transactional migrations using a schema version. Rehearse upgrades from an old fixture with retained histories/bookmarks. Measure pagination, export and startup in the actual SQLite-WASM/OPFS runtime at representative selection and regeneration counts; evaluate the composite index and deterministic tie ordering there.

**Tradeoff.** Migration fixtures and bookkeeping add maintenance; indexes cost disk space and write work. In return, upgrades become reproducible and larger libraries can avoid repeated full scans.

**Caveat.** The diagnostic used host SQLite, not the extension's WASM runtime, and measured query plans, not latency. The 1,005-record export regression passes; there is no measured user-visible performance claim. No schema or existing user data was changed in this cleanup.

**Open questions.** What library size and number of runs per selection should be supported? Must every prior run remain indefinitely? Is forward-only migration sufficient, or must older extension builds reopen upgraded databases?

### 4. Separate settings drafts from provider-test execution

**Finding.** [Settings.tsx](../src/app/Settings.tsx) combines profile normalization, draft edits, origin/key handling, validation, saving, network tests, on-device preparation, cancellation and rendering. The active provider config exists both as `openaiCompatible` and in `profiles`; `profilesWithCurrent()` synchronizes the copies on switch/save.

**Reasoning.** Adding providers or profile operations increases the number of paths that must preserve the right draft and credentials. The current browser test proves important switching behavior, but the ownership of the active draft remains implicit.

**Recommendation.** Extract a draft controller with explicit edit/switch/save operations and a separate cancellable provider-test hook. Keep the persisted format initially; choose one in-memory owner for each profile's config and adapt to the legacy top-level config at the storage boundary. Split visual sections only where that improves readability.

**Tradeoff.** Some indirection and migration tests in exchange for testable draft behavior and smaller UI responsibilities.

**Caveat.** The existing credential-separation/browser tests pass. Component length alone is not a reason to rewrite this now; preserve endpoint-origin key clearing, unsaved-navigation protection and user-triggered model preparation.

**Open questions.** Are profile deletion/import and additional provider types actually planned? Should editing remain possible during Save? Should switching profiles always hide a key previously revealed in another profile?

Prioritize explicit run semantics and message contracts before expanding reading actions/providers; introduce migrations before changing storage again. The settings extraction can wait for the next substantive settings feature.
