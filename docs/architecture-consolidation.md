# Architecture consolidation

## Baseline and accepted scope

At `e741632`, a Call batch and an EZ lookup can run through the same signed
credential owner. Each helper request starts in a separate process. Replacing
the key between requests can affect an active batch. The accepted
[coordination decision](adr/0008-coordinate-shared-connection-work.md) defines
the admission, recovery and compatibility work. A dedicated Stop prompt is
deferred. The existing Stop action is sufficient.

The baseline has 750 tracked files and about 4.8 MB of Git blob content.
An inventory of static relative imports and literal dynamic imports among 251
Saul implementation files found 814 distinct edges including type references.
The only multi-file strongly connected group in that inventory was
`configuration/connections.ts` and `configuration/definition.ts`. At the
feature level there are additional dependencies in both directions between
Calls and Annotations. These counts describe the source tree at the baseline.

## Target dependencies and delivery order

| Caller                                | May depend on                                                                                     | Boundary to enforce                                                                                                       |
| ------------------------------------- | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Chrome views and SwiftUI lookup views | Feature commands and observed state                                                               | UI cannot own durable setup or issue its constituent writes.                                                              |
| Reading, Calls and Annotations        | Frozen configuration, provider adapters, History, neutral values                                  | Calls and Annotations consume Custom Actions. Generic text comparison is shared. Configuration cannot reach into Reading. |
| LookupSession                         | Draft/request values, attempt commands, history read/selection interfaces, saved route resolution | AppModel composes LookupSession. LookupSession cannot reach back into AppModel or mirror attempt state.                   |
| Connection owner                      | Coordinator, config writer, status checks and credential client                                   | The coordinator is scoped to one setup. Providers cannot change saved configuration.                                      |
| History adapters                      | Operation registry, domain stores and SQLite                                                      | Protocol declares targets. Native SQL resolves indirect targets in the same transaction.                                  |

1. Fix History normalization, strict incoming writes, replay compatibility and target ownership. Verify malformed input, revision conflicts and uncertain annotation saves.
2. Move Saul feature dependencies while preserving settings and host formats. This slice can be verified without changing credentials or native lookup.
3. Extract EZ LookupSession and bind lookup controls to its commands. Verify launcher, retry, reuse, cancellation, saved selection and shutdown.
4. Implement shared credential admission, cross-app setup recovery, and native settings fencing. Exercise process death and legacy/mixed clients against isolated storage.
5. Move setup orchestration into each runtime owner. Verify Settings close, credential success with failed settings save, checked resume/discard and independent work.
6. Align names and directories where the move improves ownership. Run dependency checks, package both apps, then have a separate cleanup owner update living docs and prune proven unused code.

Target locations include Saul `src/{connections,custom-actions,reading,calls,annotations}`
and `shared/model/text-change.ts`, and EZ `Sources/EZ/{Connections,Lookup,History,Settings}`
and `Sources/EZCore/{Configuration,Connections,Execution,History,Speech}` where a
group has actual members. SwiftPM target boundaries and installed IDs remain stable.

Verification uses isolated credentials, settings, history and browser profiles.
Old setup records, old History receipts and frozen attempts are compatibility
fixtures. Release fencing during a concurrent settings commit, browser process
death during authorization, and compatibility with older batch clients require
explicit evidence before claiming the new cross-app guarantee.
